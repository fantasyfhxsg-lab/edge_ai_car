## 0. 摘要（TL;DR）

| # | 问题 | 严重度 | 一句话证据 |
|---|---|---|---|
| **P0** | `0x100` 出现**最长 30.47 秒的整段停发** | 🔴 高 | 逐秒 `age100` 从 1179ms **单调涨到 30469ms**（连续 30 个采样点，Δ=1000ms/s）；该期间 `hb` 计数冻结 ⇒ 一帧有效 `0x100` 都没到 |
| **P0'** | 晚期出现**“低速率期”**：连续 50–58 秒内 `age100` **始终 ≥300ms** | 🔴 高 | 该期间等效速率 **< 1–2 Hz**（规格 20 Hz，实际稳态也只有 10 Hz）；`ser_now` 窗口 11 段 ≥5s 连续超阈 |
| **P1** | `0x100` 周期不达标：实测 **94–111ms**，风暴期 **254ms** | 🟠 中 | 与“取帧→推理→发送”顺序主循环绑死一致 |
| **P2** | **67% 的停发连 `0x102` 一起停**（并非只有 `0x100` 停） | 🟠 中 | 独立 `0x102` daemon 也停 ⇒ **全局停顿** |
| **P3** | `0x102` 实际 ≈100ms 且与 `0x100` **恒差约 20ms**，不是独立 200ms 定时器 | 🟡 低 | 相位锁定，84–90% 样本相差 ≤30ms |

**对车的影响**：STM32 每超阈一次即本地刹停（HOLD，PWM=0，短路制动保持），下一条有效 `0x100` 到达即自动恢复 CRUISE。风暴期约 **每 3 秒误刹一次**（≈18 次/分钟）。

**安全红线**：STM32 协议规定 **HOLD 内 60 秒**无有效 `0x100` → **LOCK**（PWM=0、LED 常亮、**停发 `0x101`、只能复位恢复**）。实测最长空档 **30.47 s 已达该阈值 51%**。**若出现一次 >60s 的停发，车将无法自动恢复。**

## 1. 观测方法与可信度

**被测从机**：STM32F407ZGT6，裸机非阻塞任务。判活规则：`0x100` 静默 ≥ `hb_timeout_ms(300)` → 本地刹停进 HOLD；HOLD 唯一恢复条件 = 收到有效 `0x100`；`lock_timeout_ms = 60000`。

**两路独立观测**（都不干扰板端）：
1. **非停机 SWD 内存直读**：不停 CPU、不复位、不烧写，读 `0x100/0x102` 最后接收时刻、帧计数、CAN 寄存器；
2. **STM32 串口日志**：115200 8N1，1 秒一行状态（`req` 每行 +5，`0x101` 为 200ms 一帧 ⇒ 可校验“1 行 = 1 秒”）。

**对照实验（排除仪器干扰）**：先停掉 SWD 采样，再整个杀掉调试器，**只剩串口**，现象完全一致 ⇒ 停顿**不是**观测造成的。

**总线侧全程零错误**：

```
[CAN] TxErr=0 RxErr=0 BusOff=0 Ovf=0 Rec=0      （四个窗口全程）
dup=0  bad=0                                     （无重复帧、无非法帧）
```

其中 **`Ovf=0` 是决定性证据**：若 STM32 来不及收，3 级 RX FIFO 在静默 1.2s 内应溢出约 9 次 ⇒ `Ovf` 必 >0。它是 **0** ⇒ **停发期间总线上确实一帧都没有**，不是 STM32 丢帧。

**STM32 侧自证**：`0x101`（STM32→板端，规格 200ms）实测 **195ms，完全合规**；全程无 Bus-Off、无错误帧 ⇒ **STM32 的定时器、CAN 外设、总线物理层均正常**，问题只在板端产物。另外 `dup=0 bad=0` ⇒ 板端 `byte3` 每帧递增，**不存在“同一帧被重复接收”的假象**。

## 2. 问题一（P1）：`0x100` 周期不达标，且与推理耗时强耦合

| 项目 | 规格 | 实测 |
|---|---|---|
| `0x100` 周期 | **50ms**（协议 §5） | 安静期均值 **94.1ms**（中位 98 / p90 100 / p99 110 / max 128）；另两窗口 **96ms**、**111ms** |
| `0x100` 间隔分布（安静期，SWD 185s / 1828 帧） | — | <150ms 占 **99.836%**；**150–300ms 区间 0 帧**；≥300ms 占 **0.164%** |
| `0x100` 平均投放间隔（风暴期） | — | **254ms**（≈ 60% 的 `0x100` 帧没到） |
| `0x101`（STM32→板端，对照组） | 200ms | **195ms ✓ 合规** |

**推断**：`0x100` 被“取帧 → 推理 → 决策 → 发帧”的顺序主循环绑死（与贵方描述一致）。**94–111ms ≈ 一帧感知的耗时**，这就是“周期不达标”的直接证据；它也是 §3 病态停发的同一病灶。

**建议**：主循环只把**最新命令写入共享变量/队列**，由**独立定时线程按 50ms 无条件发 `0x100`**，与推理耗时彻底解耦。

## 3. 问题二（P0）：`0x100` 整段停发，晚期降为“低速率”

### 3.1 四个窗口总览

**总观测 1817 秒（30.3 分钟），判活超阈 277 次 = 9.1 次/分钟**（每一次都对应一次真实刹停）：

| 窗口 | 观测时长 | 超阈次数 | 次/分钟 | ≥5s 的连续超阈段 | 最长 `0x100` 真实空档 |
|---|---|---|---|---|---|
| `ser_long` | 146 s | 1 | 0.4 | 0 | 0.66 s |
| `ser_long2` | 174 s | 3 | 1.0 | 0 | 1.02 s |
| `ser_ctrl` | 898 s | 95 | 6.3 | 1 | 4.84 s |
| `ser_now` | 599 s | 178 | **17.8** | **11** | **30.47 s** |
| **合计** | **1817 s** | **277** | **9.1** | **12** | **30.47 s** |

**恶化趋势（本会话连续四窗口）**：`0.4 → 1.0 → 6.3 → 17.8` 次/分钟，**30 分钟内恶化约 44 倍**，且未见收敛。

### 3.2 停发到底有多长

- **稳态**：偶发**单次 0.3–5 s** 空档（安静期多数窗口全程 0 次）。
- **病态**：出现**单调增长的长空档** —— 逐秒 `age100` 从 1179ms 一路涨到 **30469ms**（连续 30 个采样点，Δ=1000ms/s）⇒ **真实连续停发 30.47 秒**。同类还有 **12.95 s** 的一例（1179→12949 单调增长）。
- **晚期叠加“低速率期”**：连续 **50 s / 58 s** 的窗口内 `age100` **始终 ≥300ms**（段内夹杂稀疏帧，并嵌套出现 5–26 s 的真实空档）⇒ 该期间 `0x100` 等效速率 **< 1–2 Hz**。
- 全局 `age100` 分位（本批窗口，含病态段）：**p50 = 79ms，p90 = 2039ms，p99 = 19.5 s，max = 30.5 s**。

> 注：**p90 = 2 s** 意味着**本批窗口里 10% 的时间 `0x100` 已经沉寂超过 2 秒** —— 这在安静期是不存在的（安静期 p99 仅 110ms）。

### 3.3 两族现象（**给板端排查的最关键分辨点**）

逐条核对每次超阈时刻 `0x100` 与 `0x102` 的龄期（共 207 个 HOLD 采样点）：

| 族 | 判据 | 次数 | 占比 | 含义 |
|---|---|---|---|---|
| **A** | `0x100` 与 `0x102` **一起**静默（两者龄期均 ≥300ms 且彼此差 <60ms，均值约 1074ms） | 139 | **67%** | **独立 `0x102` daemon 也停了** ⇒ 全局停顿 |
| **B** | **只有 `0x100` 静默**，`0x102` 仍新鲜 | 68 | **33%** | 主线程卡住、daemon 正常 ⇒ 与贵方描述吻合 |

**Family B 原始样本**（`age100` 死、`age102` 活）—— 全窗口 **96 个采样点**满足 `age100 > 500ms 且 age102 < 300ms`：

```
age100=889ms   但 age102=30ms
age100=1229ms  但 age102=180ms
age100=849ms   但 age102=50ms
age100=337ms   但 age102=198ms
```

**Family A 原始样本**（两路同死、差值极小）：

```
age100=659ms  age102=680ms
age100=789ms  age102=810ms
age100=509ms  age102=520ms
```

### 3.4 一次 30.5 秒停发的完整时间线（`ser_now` 窗口，`hb=19919` 全程冻结）

```
[RDK] 0x100 TIMEOUT -> local stop (HOLD)
[RDK] st=2 cmd=3 pwm=0 ack=2 req=12011 hb=19919 ... age100=469   age102=40     <- 0x100 已停 0.47s
[RDK] st=2 cmd=3 pwm=0 ack=2 req=12016 hb=19919 ... age100=2469  age102=1000   <- 0x102 也开始变老
[RDK] st=2 cmd=3 pwm=0 ack=2 req=12026 hb=19919 ... age100=3469  age102=70     <- 0x102 闪了一帧
[RDK] st=2 cmd=3 pwm=0 ack=2 req=12056 hb=19919 ... age100=9469  age102=6070   <- 两路一起变老
[RDK] st=2 cmd=3 pwm=0 ack=2 req=12086 hb=19919 ... age100=15469 age102=12070
[RDK] st=2 cmd=3 pwm=0 ack=2 req=12161 hb=19919 ... age100=30469 age102=59     <- 30.5s！0x102 先恢复
```

- `hb=19919` **全程未变** ⇒ 这 30.5 秒内**一帧有效 `0x100` 都没有**；
- 同时段 `Ovf=0` ⇒ **总线真的没有**，不是 STM32 丢帧；
- 0x102 先恢复（`age102=59`）而 `0x100` 仍停在 30.5s ⇒ 两路**并非同一个发送者 / 同一条代码路径**。

## 4. 问题三（P3）：`0x102` 的周期与相位与规格不符

| 项目 | 规格（协议 §5） | 实测 |
|---|---|---|
| `0x102` 心跳周期 | **200ms** | 安静期 `age102` **最大值仅 130ms**（284 个样本从未超过）⇒ 实际是 ≈100ms 量级 |
| `0x102` 与 `0x100` 的相位 | 无关 | `mean(age102) − mean(age100)` **恒为约 +20ms**；两者相差 ≤30ms 的样本占 **84–90%** |

**推断**：`0x102` **不是**自由跑的 200ms 定时器，它与 `0x100` **同节拍（≈100ms）、恒差约 20ms** 在发。这与“两个独立 daemon 线程各自按定时发”的描述**不符**。

**请确认**：`0x102` 是否同时存在“**逐帧应答 `0x101`**”与“**200ms 心跳定时器**”两个来源？各自实际周期与相位是多少？为什么实测与 `0x100` 锁相？

## 5. 影响评估

- **车架空时**：风暴期电机每约 3 秒“刹一下又走”；落地即 **每分钟约 18 次误刹**，乘员体验与安全冗余都被侵占。
- **`0x100` 实际投放率**在风暴期仅约 **40%**（平均 254ms/帧）。
- 每进一次 HOLD，STM32 会持续发 `0x101` 重握手；`0x100` 一恢复即自动回 CRUISE（**判活只看 `0x100`，`0x102` 在不在都不参与判活/恢复**）。
- **调阈值的路已经堵死（已实测验证）**：安静期最长间隔仅 **109ms**（相对 200/300ms 阈值极宽松），而病态停发 **0.3–30.5 s** —— 阈值取 200ms、300ms 甚至 500ms，判定结果**完全一样**。把阈值提到 5s 以上等于**放弃失效保护**，不可接受。
- **LOCK 风险（安全）**：30.47s 已达 60s LOCK 阈值的 **51%**。一旦某次停发超过 60s，STM32 进入 LOCK：**停发 `0x101`、PWM=0、需人工复位**，此时板端的重握手**也无法把它救回来**。

## 6. 请板端回答的问题（按重要性排序）

1. **`0x100` 是“无条件周期发”还是“有新决策才发”？**
   实测出现 **30.47 秒一帧 `0x100` 都没有**。若是“有决策才发”，这段空档可能是**正常**的（如连续无有效目标）—— 那么板端语义与 STM32 的 300ms 判活**根本不兼容**，这才是根因，需双方重议协议；若是“无条件周期发”，那就是 bug。**请优先回答这条。**
2. `0x100` 与 `0x102` 的发送**是否共用一把锁、或共用同一个 CAN 适配器写句柄**？
   若是，主线程写阻塞时持锁，`0x102` daemon 会跟着一起卡住、一起恢复（**最吻合占 67% 的 Family A**）。
3. 板端是否 **Python**？是否存在**长时间持有 GIL 的 C 调用**（大矩阵/编解码/未释放 GIL 的绑定）？这会让**所有** Python 线程一起停。
4. 运行环境是否 **容器/VM/限核（cgroup CPU quota）/低内存**？“全进程停 0.4–30s”是 **CPU 配额限流、VM 冻结、内存换页抖动（swap thrash）** 的典型症状，YOLO 负载下很常见。
5. **USB-CAN 适配器链路**：Windows「USB 选择性暂停」/ 集线器供电 / 驱动 —— 0.4–30s 的 USB 级停顿与实测吻合，建议**关掉省电做 A/B 对比**。
6. **`0x102` 的实际周期与来源**（见 §4）。
7. 能否提供**板端自身**的 `0x100` / `0x102` 发送时刻日志？

## 7. 建议修改（按优先级）

1. **解耦 `0x100` 发送**：主循环只把“最新命令”写入共享变量/队列，由**独立定时线程按 50ms 无条件发 `0x100`**。这一条同时解决 P1 与 Family B。
2. **查 `0x100` / `0x102` 是否共用锁或共用写通道**，把两条发送路径解耦；任何 CAN 写操作**不得持锁阻塞**。
3. **查全局停顿源**：GIL 长持有 C 调用 / CPU 配额限流 / 内存换页 / VM 冻结 / USB 选择性暂停 / 热降频。
   **判别口径：卡顿时 `0x100` 与 `0x102` 是不是一起停**（一起停 = 全局问题；只有 `0x100` 停 = 主循环耦合问题）。
4. **`0x102` 周期自证**：确认心跳实际周期（实测 ≈100ms，规格 200ms）及与 `0x100` 的相位关系。
5. **明确 `0x100` 的发送语义**（无条件周期发 vs 有决策才发）并同步 STM32 侧；若为后者，需双方重议判活策略（例如“连续 N 帧丢失/超过 T ms 才刹停”）。
6. **保底安全**：无论最终怎么修，**都不能让 `0x100` 静默超过 60 秒**（否则 STM32 LOCK，只能复位）。

## 8. 板端自测方法（建议照做）

在板端记录**每帧 `0x100` 与 `0x102` 的发送时刻**，输出：

1. 各自**相邻间隔直方图** —— `0x100` 是否 ≈50ms（现状 94–111ms）、`0x102` 是否真为 200ms（现状 ≈100ms）；
2. **`t(0x102) − t(0x100)` 的分布** —— 若恒为 0–20ms，说明两者其实同源/锁相，而非独立 daemon；
3. 逐次**停顿事件**记录：停了多久、**是两路一起空还是只有 `0x100` 空**、以及**当次停顿前后程序在干什么**（推理 / 写盘 / USB / 日志）；
4. 在 `0x100` 与 `0x102` 的**发送入口**各打一个点，标注是否取同一把锁 / 同一个适配器句柄；
5. 复现时同步记录 **CPU 占用 / 内存 / swap / dmesg**（USB 重枚举、OOM、throttling）。

## 9. 附录：原始样本与字段说明

**安静期（正常）**

```
[RDK] st=1 cmd=1 pwm=300 ack=2 req=9502 hb=18056 dup=0 bad=0 v=0cm/s buzz=0 age100=209 age102=320
[CAN]   TxErr=0  RxErr=0  BusOff=0  Ovf=0  Rec=0
```

**Family B（`0x100` 死、`0x102` 活）—— 下一条 `0x100` 到达即自动回 CRUISE**

```
[RDK] st=2 cmd=1 pwm=0 ack=2 req=9892 hb=18674 ... age100=809 age102=70
[RDK] 0x100 TIMEOUT -> local stop (HOLD)
[RDK] st=1 cmd=1 pwm=300 ...              age100=59  age102=70
```

**Family A（两路同死）**

```
[RDK] st=2 cmd=1 pwm=0 ack=2 req=9387 hb=17946 ... age100=659 age102=680
[RDK] 0x100 TIMEOUT -> local stop (HOLD)
```

**状态字段说明**

| 字段 | 含义 |
|---|---|
| `st` | 1 = CRUISE、2 = HOLD、0 = STATIC、3 = LOCK |
| `cmd` | 最近一次**有效 `0x100`** 的 byte0（0 停车 / 1 巡航 / 2 预警 / 3 制动；0xFF = 尚未收到） |
| `pwm` | 当前电机输出（HOLD/LOCK 时为 0，且短路制动保持） |
| `req` | `0x101`（STM32→板端）发送计数，每 200ms +1 |
| `hb` | **有效 `0x100` 接收计数**（去重通过即 +1，STATIC/LOCK 期间同样累计）—— **冻结即代表没有有效 `0x100` 到达** |
| `ack` | **仅 STATIC 握手阶段**累计的有效 `0x102` 应答（byte1=0x01）帧数；进 CRUISE 后冻结不再增加（byte1=0x02 心跳不计数） |
| `dup` | `byte3`（计数）与上一帧相同 → 去重丢弃的帧数；丢弃时**不刷新** `age100`。本批全 0 ⇒ 板端 `byte3` 每帧递增 |
| `bad` | DLC≠8 或 `byte0`（cmd）越界 → 拒收的帧数；拒收同样**不刷新** `age100`。本批全 0 |
| `age100` / `age102` | 距最近一帧**有效** `0x100` / 最近一帧 `0x102`（应答或心跳）的毫秒数 |
| `v` / `buzz` | 车速（cm/s）/ 蜂鸣状态 |

**原始数据**：4 个窗口的串口日志与 SWD 逐帧采样 CSV 均保留，可向 STM32 侧索取。
